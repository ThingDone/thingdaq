# M7 hardware measurements after board recovery

Five standalone timing jobs passed on the recovered Teensy 4.0, serial
`20428100`, at 450 MHz. The subsequent production baseline programmed and
answered identity/health queries, but failed watchdog acceptance while idle.
No acquisition cell ran and no C acquisition variant was uploaded. The final
successfully programmed image is the original production baseline,
`thingdaq-6f2c6b332efc9280`; sustained operation is not qualified.

The main findings are an approximately **22.5% reduction in uncontended event
publish/take cycles** using atomics at `-O2`, no packing improvement from `-O3`
over `-O2`, and no C/C++ difference after controlling function alignment.
Moving the aligned packing kernel from warm flash to ITCM saved only 13 cycles
per 2,024 samples. These results do not justify changing production interrupt
guards or moving this kernel into scarce ITCM yet.

## Method and timing results

The existing standalone sketch tests the same packing body compiled as C11 and
C++17, crossed with flash/ITCM code placement and DTCM/OCRAM input placement.
Output is in DTCM. The compiler is pinned Arm GNU 15.2.1, Teensy core 1.62.0.
Every job completed five passes, each with 101 trials per case. The collector
validated all ten cases, their counts, ordered timings, serial identity and
independent output digests. All packer digests were `1784290555`; event totals
were 256. The archived ELF hash was checked and HEX regenerated from that ELF
before submission.

Numbers below are the median of the five pass medians, in DWT cycles per 2,024
samples. Every pass median was identical for each case. Warm DTCM and OCRAM
inputs produced the same medians. The last row is a new layout-control build;
the other four retain their original compiler-selected layouts.

| Standalone build | C flash | C ITCM | C++ flash | C++ ITCM |
| --- | ---: | ---: | ---: | ---: |
| `-Os` | 52,684 | 54,694 | 52,683 | 52,670 |
| `-O1` | 62,803 | 62,789 | 62,803 | 62,790 |
| `-O2` | 50,651 | 48,614 | 48,627 | 50,638 |
| `-O3` | 50,652 | 48,614 | 48,627 | 50,638 |
| `-O2 -falign-functions=32` | 48,627 | 48,614 | 48,627 | 48,614 |

The aligned result is approximately 24 cycles/sample. Its flash/ITCM difference
is 0.027% of the flash time. This is a warm-cache measurement with CPU-filled
input, not a measurement immediately after DMA cache invalidation. Timings
include call, fence and timer overhead, without subtraction. Interrupts remain
enabled except inside the individual PRIMASK operations. Recorded maxima include
incidental interrupts and USB activity; they are not worst-case latency bounds.

### Layout control

The original `-O2` build appeared to favor C in ITCM and C++ in flash despite the
same kernel instructions. The aligned build removed that difference:

| Kernel | Original `-O2` address | Aligned `-O2` address | Bytes |
| --- | --- | --- | ---: |
| C flash | `0x60001614` | `0x60001640` | 218 |
| C++ flash | `0x600016f0` | `0x60001720` | 218 |
| C ITCM | `0x20` | `0x20` | 218 |
| C++ ITCM | `0xfc` | `0x100` | 218 |

This is evidence of a layout confound, not an inherent language advantage.
Extracting each function's bytes from the hash-verified linked ELF confirmed
that all four kernels are byte-identical within each build, including the
aligned build. The `-O2` and `-O3` kernel bytes also match each other.
The alignment flag affects the whole standalone build, so this follow-up does
not isolate a particular fetch boundary or microarchitectural mechanism.
`m7_performance.py --benchmark-alignment 32` uses a separate output directory,
records the flag in its manifest and rejects any packer whose actual linked
address is not aligned. Production flags were not changed.

### Event publication

Each measured batch contains 256 publish/take pairs. The atomic implementation
uses release OR and acquire exchange; the control saves/disables/restores
PRIMASK around each operation. These are coalescing notification words, not DMA
buffer ownership protocols. Values are median batch cycles:

| Build | PRIMASK | Atomic |
| --- | ---: | ---: |
| `-Os` | 10,779 | 7,962 |
| `-O1` | 10,780 | 7,964 |
| `-O2` | 10,261 | 7,955 |
| `-O3` | 10,258 | 7,955 |
| `-O2`, aligned | 10,261 | 7,955 |

At `-O2`, this is 40.082 versus 31.074 cycles/pair, a 22.47% reduction. The test
does not introduce ISR contention on the word or measure exclusive-access
retries, interrupt latency or acquisition CPU utilization. Production guards
remain unchanged. Whole-firmware `-O3` still fails the existing stack floor;
passing the small standalone sketch does not qualify that acquisition image.

## Baseline acquisition preflight

The planned SDK job was five 12-second acquisition cells, covering ADC, GPIO,
combined streams and both auxiliary-bank modes. It used the hash-verified
baseline from the original compiler campaign, with new `--runtime-health`
sampling enabled. Connection verified the expected serial/build identity,
protocol 2, 450 MHz clock and fixed 1 MHz profile support. Its first idle health
sample reported:

| Field | Observation |
| --- | ---: |
| Stack watermark available | true |
| Stack total | 34,432 bytes |
| Minimum free stack | 28,664 bytes |
| Maximum used stack | 5,768 bytes |
| Watchdog enabled | **false** |
| Watchdog timeout | **0 ms** |
| Retained reset cause | `0x1` |

The collector stopped at its watchdog assertion, before the clock diagnostic
or START. The raw result contains an empty assertion message because that run
preceded the addition of descriptive health assertion messages. The saved
health row identifies the failed condition. Programming succeeded, the Python
test exited 1, and the job is **TEST_FAIL**, despite the service's outer success
status. No USB disconnect was reported during this short preflight.

In `watchdog_teensy.cpp`, the reported enabled state requires both successful
initialization/register verification and the current hardware enable bit.
Consequently the observation does not establish whether the hardware enable
bit itself was clear. `refresh()` also depends on the internal successful-init
flag. No raw watchdog register trace was collected, so the failed initialization
stage and any connection to the September 18 USB disconnect remain unknown.
The idle stack sample is not an acquisition watermark.

The watchdog health failure must be resolved before comparing the full C flash
and C ITCM acquisition variants. No build or health gate was relaxed. The
service postflight reported normal mode, reachable worker/Docker/hub and queue
depth zero; that describes the rig, not sustained firmware health.

To reproduce the layout-control build and measurement with a fresh evidence
directory:

```bash
python3 firmware/tools/m7_performance.py \
  --benchmark --optimization O2 --benchmark-alignment 32
python3 firmware/tools/run_m7_benchmark.py \
  --build-dir firmware/build/m7-performance/benchmark-O2-align32 \
  --evidence-dir doc/results/raw/m7-hardware-next/benchmark-O2-align32 \
  --service http://192.168.150.14:5000
```

`run_input_isolation.py --host-api --runtime-health` samples health at idle,
before/during/after each acquisition cell and records midpoint STATUS for
packer CPU comparison. Each health observation is retained and printed before
acceptance checks, including failed observations. Regression tests exercise
disabled sampling and unavailable/exhausted stack or unvalidated watchdog
rejection. In this hardware run only the initial idle sample was reached;
mid-capture telemetry remains untested on the board.

Local validation passed 34 focused tooling, C/atomic correctness and
documentation tests, with 731 subtests. Ruff lint/format and whitespace checks
passed. The aligned target build also verified all four function addresses.
These checks validate the tooling and recorded experiment; they do not turn
the failed baseline acquisition preflight into a pass.
